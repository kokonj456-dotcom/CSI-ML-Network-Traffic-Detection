# สคริปต์บทเรียนเสียง: ทำความเข้าใจ Data Pipeline ตั้งแต่ไฟล์ดิบจนถึงฟีเจอร์สำหรับโมเดล

> สคริปต์นี้เรียบเรียงจาก README และเอกสารใน Data Pipeline ทั้งหมด รวมถึงคำอธิบายใน Markdown ของ Notebook ทั้ง 9 เล่ม โค้ดจริงและข้อมูลดิบจำนวนมากไม่ได้อ่านทีละบรรทัด แต่จะอธิบายว่าทำอะไร ทำไปทำไม ได้ผลอย่างไร และควรแปลผลอย่างไร
>
> ตัวเลขที่กล่าวถึงเป็น snapshot จากรายงานที่มีอยู่ในเครื่อง ณ วันที่จัดทำ หากรัน pipeline ใหม่แล้วได้ตัวเลขต่างออกไป ให้ยึดรายงานที่สร้างจากข้อมูลรอบล่าสุดเป็นหลัก

## บทที่ 1: มองภาพรวมก่อน

สวัสดีครับ บทเรียนนี้จะพาเดินทางไปกับข้อมูลเครือข่าย ตั้งแต่ไฟล์ต้นฉบับ ไปจนถึงตารางตัวเลขที่พร้อมส่งให้โมเดล โดยจะใช้สองชุดข้อมูล คือ NSL-KDD และ UNSW-NB15

ให้นึกภาพว่ามีสมุดบันทึกเหตุการณ์เครือข่ายสองเล่ม แต่ละเล่มใช้คำและรูปแบบไม่เหมือนกัน เป้าหมายของ Data Pipeline คือสำรวจสมุดทั้งสองเล่ม ทำความสะอาดสิ่งที่ทำให้สับสน แล้วแปลงเฉพาะข้อมูลที่มีความหมายเทียบกันได้ให้เป็นรูปแบบกลาง จากนั้นค่อยแบ่งข้อมูลและสร้างคอลัมน์ที่โมเดลอ่านได้

เส้นทางหลักมีแปดช่วง เริ่มจาก Raw ซึ่งเป็นไฟล์ต้นฉบับ ต่อด้วยการตรวจไฟล์และบันทึกที่มา จากนั้นทำ EDA เพื่อสำรวจ ทำ Cleansing เพื่อจัดรูปแบบและตรวจความถูกต้อง ทำ Harmonization เพื่อแปลงเป็นชื่อและความหมายกลาง นำผลของแต่ละชุดมาสร้าง Dataset กลาง แบ่ง Train, Validation และ Test แล้วทำ Feature Engineering กลางเป็นขั้นสุดท้ายก่อนส่งให้โมเดล

จุดสำคัญคือแต่ละ Dataset ทำ EDA, Cleansing และ Harmonization ของตัวเองก่อน ส่วนโฟลเดอร์ common ไม่ทำสามขั้นนี้ซ้ำ common รับเฉพาะผล Harmonization ที่ผ่านการตรวจแล้ว มารวม แบ่งชุด และทำ Feature Engineering กลาง

จำตัวอักษรสามตัวนี้ไว้ก่อน เอ็กซ์ หรือ X คือคุณลักษณะพฤติกรรมที่โมเดลอ่าน เช่น ระยะเวลาและจำนวนไบต์ ส่วนวาย หรือ y คือคำตอบอ้างอิง เช่น Normal หรือ Attack และ metadata คือข้อมูลช่วยตามรอย เช่น มาจาก Dataset ไหนหรือเป็นแถวลำดับใด สำหรับ Isolation Forest แบบ unsupervised จะฝึกด้วย X เท่านั้น ไม่ส่ง y เข้าไป แต่เก็บ y ไว้เทียบผลหลังจากโมเดลให้คะแนนแล้ว

ทุกขั้นเก็บผลแยกจาก Raw เสมอ ไฟล์ต้นฉบับเปรียบเหมือนหลักฐานต้นทาง ห้ามแก้ทับ เพราะถ้าพบว่ากฎการแปลงผิด เราจะได้กลับมาเริ่มใหม่ได้

นอกจากเนื้อหาใน Notebook แล้ว มี registry ที่บอกว่ามี Dataset ใดบ้าง และ feature contract ที่ระบุชื่อ ความหมาย หน่วย และสูตรของคอลัมน์กลาง เมื่อไฟล์ดิบเปลี่ยน checksum หรือที่เรียกว่าลายนิ้วมือดิจิทัลจะเปลี่ยน ระบบจึงตรวจเจอและไม่ควรนำผล Harmonization รุ่นเก่ามาปนกับข้อมูลรุ่นใหม่

ผลส่วนใหญ่บันทึกเป็น CSV เพราะเปิดดูได้ด้วย Excel, VS Code หรือโปรแกรมอ่านข้อความทั่วไป ข้อแลกเปลี่ยนคือไฟล์อาจใหญ่และอ่านช้ากว่า Parquet แต่ใน Pipeline รุ่นนี้เลือก CSV เพื่อให้ง่ายต่อการตรวจสอบด้วยเครื่องมือที่สมาชิกทีมคุ้นเคย

เหตุผลที่แยก EDA, Cleansing และ Harmonization ไว้ในแต่ละ Dataset ก่อน แล้วค่อยมี common คือข้อมูลต้นทางไม่ได้มีชื่อคอลัมน์ หน่วย และรายละเอียดเหมือนกัน ถ้ารวมตั้งแต่ต้น เราอาจเผลอคิดว่าคอลัมน์ชื่อคล้ายกันแปลว่าเหมือนกันจริง ที่มาของการตัดสินใจนี้คือ schema และ feature contract ของโปรเจกต์ ซึ่งระบุทั้งชื่อ หน่วย ความหมาย และคอลัมน์ต้นทาง ผลที่ได้คือเรายังตามย้อนกลับได้ว่า record มาจากไฟล์และแถวใด และ common รับเฉพาะข้อมูลที่แปลงตามกติกาแล้ว

## บทที่ 2: NSL-KDD คืออะไร และ EDA บอกอะไร

เริ่มจาก NSL-KDD หนึ่งแถวแทนบันทึกการเชื่อมต่อเครือข่ายหนึ่งรายการ ไม่ใช่หนึ่งแพ็กเก็ต ไฟล์มีข้อมูลเชิงพฤติกรรม คำตอบ label และ difficulty ซึ่งเป็นข้อมูลประกอบของ benchmark รวม 43 คอลัมน์

Notebook EDA หรือการสำรวจข้อมูล ใช้ไฟล์ KDDTrain+ จำนวน 125,973 แถว 43 คอลัมน์ จุดประสงค์ไม่ใช่แก้ข้อมูลหรือฝึกโมเดล แต่เพื่อดูว่าข้อมูลหน้าตาอย่างไร มีค่าว่างหรือแถวซ้ำหรือไม่ การโจมตีกระจายแบบไหน และตัวเลขมีรูปทรงอย่างไร

ผลสำรวจรอบนี้ไม่พบ missing และไม่พบแถวซ้ำที่เหมือนกันทุกคอลัมน์ แต่ num_outbound_cmds เป็นศูนย์ทุกแถว จึงเป็นคอลัมน์คงที่ ไม่มีความสามารถช่วยแยก record ส่วน difficulty เป็นข้อมูลของ benchmark ไม่ใช่พฤติกรรมเครือข่าย จึงไม่ควรใช้เป็นเบาะแสของโมเดล

ใน Train มี Normal 67,343 แถว หรือประมาณ 53.46 เปอร์เซ็นต์ ส่วนการโจมตีรวมประมาณ 46.54 เปอร์เซ็นต์ แต่ภายในกลุ่มโจมตีไม่ได้มีจำนวนเท่ากัน DoS มีประมาณ 36.46 เปอร์เซ็นต์ของข้อมูลทั้งหมด Probe 9.25 เปอร์เซ็นต์ R2L 0.79 เปอร์เซ็นต์ และ U2R 0.04 เปอร์เซ็นต์ ตัวอย่างเช่น neptune เพียงชนิดเดียวมี 41,214 แถว ขณะที่การโจมตีบางชนิดมีเพียงหลักหน่วยหรือหลักสิบ

สิ่งนี้เรียกว่า class imbalance หรือจำนวนตัวอย่างไม่สมดุลกัน ถ้าดู Accuracy อย่างเดียว โมเดลอาจดูดีเพราะทายกลุ่มใหญ่ถูก แต่พลาดกลุ่มโจมตีหายาก จึงควรดู Precision, Recall, F1 และผลแยกตามประเภทด้วย

ตัวแปรเชิงหมวดหมู่มี protocol 3 หมวด, flag 11 หมวด และ service 70 หมวด คำว่า service ในที่นี้หมายถึงบริการเครือข่าย เช่น HTTP, FTP หรือ Telnet ไม่ได้เป็นชื่อการโจมตี การมี 70 หมวดทำให้ต้องสร้างตัวเลขหลายคอลัมน์ในขั้น One-Hot Encoding

ตัวเลขหลายตัวมีศูนย์เยอะและหางยาว เช่นจำนวนไบต์หรือจำนวน connection การสำรวจใช้ log1p เพื่อให้เห็นค่าต่ำและค่าสูงในกราฟเดียวกัน การนับ outlier ด้วยกฎ IQR เป็นเพียงธงทางสถิติ ไม่ได้แปลว่าค่านั้นผิด ตัวอย่างเช่น dst_bytes มีค่าที่อยู่นอกกรอบ IQR ประมาณ 18.72 เปอร์เซ็นต์ แต่ traffic ที่สุดโต่งอาจเป็นพฤติกรรมโจมตีจริง จึงไม่ลบทิ้งอัตโนมัติ

กราฟเปรียบเทียบ Normal กับ Attack ใช้ตัวอย่างไม่เกิน 25,000 แถวด้วย seed 42 เพื่อให้รันเร็วและทำซ้ำได้ จุดในกราฟที่ซ้อนกันมากแปลว่าตัวแปรเดี่ยวอาจแยกกลุ่มไม่ชัด แต่รูปแบบของหลายตัวแปรรวมกันอาจยังช่วยได้ ความสัมพันธ์หรือ correlation ก็เป็นเพียงการเคลื่อนไหวร่วมกัน ไม่ได้พิสูจน์ว่า feature เป็นสาเหตุของการโจมตี

ตัวอย่างผล correlation กับ is_attack ใน Train ได้แก่ same_srv_rate ประมาณลบ 0.752, dst_host_srv_count ลบ 0.723, dst_host_same_srv_rate ลบ 0.694, logged_in ลบ 0.690 และ dst_host_srv_serror_rate บวก 0.655 ค่าเหล่านี้อธิบายความสัมพันธ์เชิงเส้นในข้อมูลชุดนี้เท่านั้น ไม่ได้บอกว่าเมื่อเปลี่ยน feature แล้วจะทำให้เกิดหรือหยุดการโจมตี

ทำ EDA ไปทำไม? เพื่อให้รู้ก่อนว่าควรตรวจหรือแปลงอะไร แทนที่จะเดากฎ cleansing ล่วงหน้า ที่มาของตัวเลขในบทนี้คือการอ่าน KDDTrain+ จริงและรายงาน EDA ที่สร้างจากไฟล์นั้น เช่น จำนวนแถว สัดส่วน label ค่าซ้ำ missing การกระจาย และความเบ้ ผลที่ได้ไม่ได้สั่งให้ลบค่าที่ดูแปลก แต่ชี้ว่าควรเก็บคอลัมน์คงที่ออกจากตัวแทนโมเดล พิจารณา log transform กับตัวเลขหางยาว และระวังคลาสหายากตอนประเมินผล

กราฟตัวอย่างใช้ sample เพื่อให้คำนวณเร็ว ส่วนตารางนับและรายงาน schema ใช้ตรวจข้อมูลเต็มตามที่ Notebook ระบุ ดังนั้นให้อ่านกราฟเป็นภาพช่วยตั้งคำถาม ไม่ใช่หลักฐานว่าทุกแถวมีการกระจายเหมือน sample และอย่าอ่าน correlation ว่าเป็นเหตุและผล

## บทที่ 3: อ่านคอลัมน์ดิบ NSL-KDD ทั้ง 43 ช่อง

คราวนี้เราจะเดินดูคอลัมน์ทั้ง 43 ช่อง เพื่อให้เห็นว่าอะไรเป็นข้อมูลเครือข่าย อะไรเป็นคำตอบ และอะไรถูกตัดออก

กลุ่มแรกคือข้อมูลการเชื่อมต่อพื้นฐาน คอลัมน์ duration บอกเวลาที่ใช้เชื่อมต่อเป็นวินาที protocol_type บอกโปรโตคอล เช่น TCP, UDP หรือ ICMP service บอกบริการปลายทาง และ flag บอกผลหรือสถานะของการเชื่อมต่อ เช่น สำเร็จ ถูกปฏิเสธ หรือ reset

src_bytes คือจำนวนไบต์จากต้นทางไปปลายทาง ส่วน dst_bytes คือไบต์ที่ปลายทางส่งกลับ land เป็นตัวบ่งชี้ว่า source กับ destination เป็น host และ port เดียวกันหรือไม่ wrong_fragment นับ fragment ที่ผิดรูปแบบ และ urgent นับแพ็กเก็ตที่ตั้ง urgent bit

กลุ่มถัดไปเกี่ยวกับเนื้อหาและกิจกรรมบัญชี hot นับกิจกรรมที่จัดอยู่ในกลุ่ม hot num_failed_logins นับการเข้าสู่ระบบที่ล้มเหลว logged_in บอกว่าการเข้าสู่ระบบสำเร็จหรือไม่ num_compromised นับสัญญาณว่าระบบถูก compromise root_shell บอกว่ามี root shell หรือไม่ su_attempted บอกการพยายามใช้สิทธิ์ su root และ num_root นับกิจกรรมในฐานะ root

num_file_creations นับการสร้างไฟล์ num_shells นับการเรียก shell num_access_files นับการทำงานกับไฟล์ควบคุมสิทธิ์ num_outbound_cmds เป็นตัวนับคำสั่งขาออกใน FTP ซึ่งในข้อมูลรอบนี้เป็นศูนย์ทุกแถว จึงถูกลบ is_host_login เป็น flag เกี่ยวกับชนิด login โดยเอกสารต้นทางมีคำอธิบายชื่อที่ต่างกัน จึงควรยึดความหมายตาม schema ของชุดข้อมูล และ is_guest_login บอกว่าใช้ guest account หรือไม่

คอลัมน์กลุ่มที่สามคือสถิติ traffic ตาม host และ service เป็นข้อมูลสรุปของ connection รอบข้าง ไม่ใช่ตัวนับที่โมเดลสร้างสด ๆ เอง count นับ connection ในกลุ่มปลายทาง host เดียวกัน srv_count นับ connection ที่ใช้ service เดียวกัน

serror_rate และ srv_serror_rate คืออัตรา SYN error เมื่อมองกลุ่ม host และกลุ่ม service ตามลำดับ rerror_rate และ srv_rerror_rate คืออัตรา reject หรือ error ในสองบริบทเดียวกัน same_srv_rate คืออัตราที่ connection ใช้ service เดียวกัน diff_srv_rate คืออัตราที่ใช้ service ต่างกัน และ srv_diff_host_rate บอกว่า service เดียวกันถูกใช้กับ host อื่นมากน้อยเพียงใด

dst_host_count นับกิจกรรมที่สัมพันธ์กับ destination host dst_host_srv_count นับกิจกรรมของ host และ service เดียวกัน dst_host_same_srv_rate และ dst_host_diff_srv_rate สรุปการใช้ service ที่เหมือนหรือต่างกันในกลุ่ม host

dst_host_same_src_port_rate บอกการใช้ source port เดิมกับ destination host dst_host_srv_diff_host_rate บอกการกระจายของ connection service เดียวกันระหว่าง host ต่าง ๆ dst_host_serror_rate และ dst_host_srv_serror_rate สรุป SYN error ระดับ host และระดับ host กับ service ส่วน dst_host_rerror_rate และ dst_host_srv_rerror_rate สรุป reject หรือ error ในสองระดับนั้น

อัตราทุกตัวที่ลงท้ายด้วย rate ควรอยู่ระหว่างศูนย์กับหนึ่ง Pipeline ตรวจช่วงนี้ ถ้าผิดจะหยุดให้ตรวจ ไม่ clip ค่าอย่างเงียบ ๆ

คอลัมน์ที่ 42 คือ label เป็นคำตอบจริงของ record เช่น normal หรือชื่อ attack ห้ามส่งเป็น feature ให้ Isolation Forest ส่วนคอลัมน์ที่ 43 คือ difficulty ซึ่งเป็นระดับความยากของ benchmark ไม่ใช่พฤติกรรม network จึงถูกลบออกใน cleansing

สรุปคือ 41 คอลัมน์แรกเป็นตัวอธิบาย connection ก่อนตัดคอลัมน์คงที่ จากนั้น label เป็นคำตอบ ส่วน difficulty เป็น metadata เมื่อเอาสามหมวดข้อความ protocol_type, service และ flag ออกจากตัวเลข 41 predictor แล้ว จะเหลือตัวเลข 37 ตัวกับหมวดหมู่ 3 ตัว

ที่มาของความหมายคอลัมน์คือคำอธิบาย schema ของ NSL-KDD และโครงสร้างไฟล์จริง ไม่ใช่การอนุมานจากชื่ออย่างเดียว เหตุผลที่แยกคอลัมน์เป็นตัวเลข หมวดหมู่ label และ metadata คือแต่ละกลุ่มทำหน้าที่ไม่เหมือนกัน: พฤติกรรมอาจเป็น X, หมวดข้อความต้องเข้ารหัสก่อนใช้ และ label ใช้เป็นคำตอบอ้างอิง ไม่ควรปนใน X ของ Isolation Forest ผลที่ได้จากการจัดกลุ่มนี้คือรู้ว่ามีตัวแปรพฤติกรรม 40 ตัวหลังตัดคอลัมน์คงที่ และมี label แยกต่างหากไว้ตรวจผลภายหลัง

## บทที่ 4: Cleansing ของ NSL-KDD

Notebook cleansing เริ่มด้วยการกำหนด schema ทั้ง 43 คอลัมน์ตามลำดับ เพราะไฟล์ Raw ไม่มีหัวตาราง ถ้าลำดับผิด ค่าทุกช่องในแถวอาจถูกแปลความหมายผิดตั้งแต่ต้น

ขั้นต่อมาคือปรับข้อความให้เป็นมาตรฐาน ตัดช่องว่างและทำ protocol, service, flag และ label เป็นตัวพิมพ์เล็ก เช่น SF, เว้นวรรค sf และ sf จะนับเป็นหมวดเดียวกัน ขั้นนี้ไม่ได้ลบ label หรือรวม attack คนละชนิดเข้าด้วยกัน

จากนั้นแปลงคอลัมน์ที่ควรเป็นตัวเลข ตรวจข้อความที่แปลงไม่ได้และค่าอนันต์ ตรวจ missing และลบเฉพาะแถวที่ไม่สมบูรณ์หากมี ตรวจแถวซ้ำแบบทุกคอลัมน์ตรงกันเป๊ะ และตรวจช่วงค่าของ rate กับจำนวนที่ไม่ควรติดลบ หากพบค่าผิด ระบบหยุดพร้อมรายละเอียดแทนที่จะปรับค่าเอง

ผลจริงของ KDDTrain มี 125,973 แถว KDDTest มี 22,544 และ KDDTest-21 มี 11,850 ทั้งสามชุดไม่มี invalid number, infinity, missing หรือ duplicate ในรอบนี้ จึงไม่มีแถวถูกลบ

ขั้น cleansing เอา difficulty ออกเพราะเป็นข้อมูล benchmark และเอา num_outbound_cmds ออกเพราะเป็นคอลัมน์คงที่ เหลือ predictor 40 ตัว คือเลข 37 กับหมวดหมู่ 3 จากนั้นสร้าง target เพิ่มสองคอลัมน์ คือ attack_family และ is_attack แต่ยังรักษา label เดิมไว้ด้วย ดังนั้นจำนวนคอลัมน์ cleaned กลับมาเป็น 43 ได้ แม้โครงสร้างจะแตกต่างจาก raw

attack_family ยุบชื่อ attack ที่รู้จักให้เป็น DoS, Probe, R2L หรือ U2R ส่วน normal ได้ Normal และชื่อที่ mapping ยังไม่รู้จักได้ Unknown is_attack เป็นศูนย์เฉพาะ normal และเป็นหนึ่งสำหรับ label อื่นทั้งหมด รวมถึง Unknown คำว่า Unknown หมายถึง mapping ยังจัดกลุ่มย่อยไม่ได้ ไม่ได้หมายความว่าเป็น normal หรือไม่มีคำตอบ

รายงาน cleansing และ schema ช่วยตรวจว่าแถวเริ่มต้นกับแถวสุดท้ายเท่ากันหรือไม่ มีค่าถูก normalize เท่าไร มีคอลัมน์ใดถูกตัด และ target กระจายอย่างไร การผ่าน cleansing บอกว่ารูปแบบข้อมูลผ่านกฎพื้นฐาน ไม่ได้รับประกันว่า record ปลอดภัยหรือโมเดลจะแม่น

เหตุผลที่ขั้นนี้ตรวจแล้วหยุดเมื่อเจอค่าผิด แทนการ clip หรือลบทุกอย่างที่ดูสุดโต่ง คือค่าผิดนิยามกับพฤติกรรมผิดปกติเป็นคนละเรื่อง โดยเฉพาะงานตรวจจับการโจมตี ค่าที่ห่างจากคนส่วนใหญ่อาจเป็นสัญญาณสำคัญได้ ที่มาคือกฎ schema และช่วงค่าที่กำหนดไว้ใน Notebook; รายงาน cleansing audit บันทึกจำนวนแถวเข้าออก การเปลี่ยนข้อความ ค่าที่ผิด และแถวซ้ำ ผลรอบนี้คือไม่ต้องลบแถว แต่ตัดคอลัมน์ benchmark และคอลัมน์คงที่ พร้อมเพิ่ม target ที่คำนวณจาก label เดิม

ดังนั้นผลลัพธ์ที่ควรอ่านคือ “ข้อมูลผ่านการตรวจตามกฎที่ประกาศไว้หรือไม่” ไม่ใช่ “ข้อมูลสะอาดสมบูรณ์แน่นอน” หากภายหลังพบแถวถูกตัด ให้เปิด audit ดูเหตุผลและจำนวนก่อนนำผลไปฝึกโมเดล

## บทที่ 5: Harmonization ของ NSL-KDD

Harmonization คือการแปลงข้อมูลแต่ละชุดให้ใช้ schema กลางร่วมกัน ไม่ใช่แค่เปลี่ยนชื่อคอลัมน์ ขั้นนี้ตรวจ checksum ของ raw เทียบกับ manifest และตรวจจำนวนแถวก่อนสร้างรหัสอ้างอิง หากจำนวนไม่ตรง ระบบหยุดแทนการเดาว่าแถวไหนตรงกับแถวไหน

ตัวอย่างการจับคู่คือ duration ของ NSL ไปเป็น duration กลาง protocol_type ไปเป็น protocol, src_bytes ไปเป็น bytes_forward และ dst_bytes ไปเป็น bytes_backward ส่วน service และ flag ถูกจัดเป็น service_group และ conn_state_group ตาม mapping ใน contract

ผลแยกเป็นสามตารางที่ใช้ record_id เชื่อมกัน ตาราง features เก็บพฤติกรรมที่อาจนำไปสร้าง X ตาราง labels เก็บ label เดิมและ taxonomy ใช้ประเมินผลภายหลัง ส่วน metadata เก็บที่มาของ record, รหัสแถวเดิม, official split, flags และข้อมูลความพร้อม

KDDTest-21 เป็นชุดย่อยสำหรับประเมิน ไม่ควรต่อเป็น record ใหม่ซ้ำกับ KDDTest+ ระบบจึงเชื่อม record ของ Test-21 กลับไปยังแถวใน Test และทำเป็น evaluation view

NSL-KDD ไม่มี packet count, TTL หรือ TCP window ที่มีนิยามตรงกับข้อมูล UNSW จึงห้ามสร้างตัวเลขศูนย์ปลอมเพื่อให้ตารางดูครบ ค่าที่ไม่มีต้องเป็น missing พร้อม availability mask และยังไม่ส่งเป็น feature ร่วมโดยอัตโนมัติ

record_id เป็นกุญแจสำหรับเชื่อมตาราง ไม่ใช่สัญญาณ traffic ก่อน fit หรือ predict ต้องตัดมันออกจาก X เช่นเดียวกับ labels และ metadata

ทำ Harmonization เพราะต้องการให้ข้อมูลสองชุดใช้ชื่อและหน่วยกลางเดียวกัน โดยยังรักษาความหมาย ไม่ใช่บังคับให้ทุกคอลัมน์มีค่า ที่มาคือ feature contract ที่ระบุว่าแต่ละฟีเจอร์มาจากช่องต้นทางใดและจับคู่ได้ด้วยเหตุผลใด ผลคือได้ตารางสามชุดที่ join กันได้ด้วย record_id พร้อม provenance และ quality flags; คอลัมน์ที่ไม่มีคู่เทียบจะคงเป็น unavailable แทนการแต่งข้อมูลขึ้นมา

การตรวจ checksum กับจำนวนแถวมีไว้ยืนยันว่ากำลังแปลงไฟล์รุ่นที่คาดไว้ และไม่จับคู่ record ด้วยตำแหน่งแบบเดาสุ่ม หากการตรวจไม่ผ่าน การหยุดคือผลลัพธ์ที่ถูกต้องกว่าไฟล์กลางที่ดูครบแต่เชื่อมผิด

## บทที่ 6: Feature Engineering เฉพาะ NSL-KDD

NSL มี feature engineering เฉพาะชุด เพื่อคงทางเลือกการทดลองกับโมเดลเดิมไว้ ขั้นนี้อ่าน cleaned CSV ตรวจ schema แล้วแยก label, attack_family และ is_attack ออกเป็น targets ก่อนสร้าง features

ตัวเลขต้นฉบับ 37 คอลัมน์ยังอยู่ครบใน full feature set ค่าที่สร้างใหม่เป็นทางเลือกเพิ่ม ไม่ได้เขียนทับข้อมูลเดิม

กลุ่มแรกมี log transform 13 คอลัมน์ ใช้สูตร log1p ของค่า x ซึ่งเท่ากับ natural log ของหนึ่งบวก x ช่วยบีบค่าที่สูงมากให้ระยะห่างลดลง แต่ยังรักษาลำดับเดิมและแปลงศูนย์ได้ คอลัมน์คือ log1p_duration, log1p_src_bytes, log1p_dst_bytes, log1p_count, log1p_srv_count, log1p_dst_host_count, log1p_dst_host_srv_count, log1p_hot, log1p_num_failed_logins, log1p_num_compromised, log1p_num_root, log1p_num_file_creations และ log1p_num_access_files

ตัวอย่าง เมื่อค่าเป็นศูนย์ log1p ได้ศูนย์ เมื่อค่าเป็นสิบจะได้ประมาณ 2.40 และเมื่อเป็นหนึ่งล้านจะได้ประมาณ 13.82 ดังนั้นค่ามหาศาลจะไม่ทิ้งระยะห่างจากค่าปานกลางมากเท่าเดิม

กลุ่มที่สองคือ indicator 14 คอลัมน์ ซึ่งบอกว่ามีเหตุการณ์หรือไม่ สำหรับคอลัมน์เดี่ยวใช้กฎ has_x เท่ากับหนึ่งถ้าค่าต้นฉบับมากกว่าศูนย์ มิฉะนั้นเป็นศูนย์ ได้แก่ has_land, has_wrong_fragment, has_urgent, has_hot, has_num_failed_logins, has_num_compromised, has_root_shell, has_su_attempted, has_num_root, has_num_file_creations, has_num_shells และ has_num_access_files

อีกสองตัวเป็นกลุ่มรวม has_root_activity เป็นหนึ่งถ้า root_shell, su_attempted หรือ num_root ตัวใดตัวหนึ่งมีค่ามากกว่าศูนย์ ส่วน has_file_or_shell_activity เป็นหนึ่งถ้า num_file_creations, num_shells หรือ num_access_files มีค่ามากกว่าศูนย์

indicator ไม่ได้สร้างข้อมูลใหม่ แต่เปลี่ยนรูปแบบเพื่อเน้นว่ามีเหตุการณ์หายากหรือไม่ ตัวอย่าง failed login เป็นศูนย์จะได้ indicator ศูนย์ ส่วนหนึ่งครั้งหรือสองครั้งจะได้ indicator หนึ่ง

กลุ่มที่สามมี aggregate หรือ feature สรุปหลายตัวเข้าด้วยกัน 9 คอลัมน์ total_bytes บวก src_bytes กับ dst_bytes, log1p_total_bytes บีบค่ารวมด้วย log, signed_log_byte_difference แสดงความต่างที่เก็บทิศทางไว้ โดยเป็นบวกเมื่อ source ส่งมากกว่าและลบเมื่อปลายทางส่งกลับมากกว่า

อีกหกตัวคือ syn_error_mean ซึ่งเฉลี่ย serror_rate กับ srv_serror_rate, reject_error_mean ซึ่งเฉลี่ย rerror_rate กับ srv_rerror_rate, overall_error_rate ซึ่งเฉลี่ย error rate ทั้งสี่, host_service_count_ratio ซึ่งหาร dst_host_srv_count ด้วย dst_host_count บวกหนึ่งเพื่อป้องกันหารศูนย์, host_service_rate_gap ซึ่งหาผลต่างของ dst_host_same_srv_rate กับ same_srv_rate และ host_error_mean ซึ่งเฉลี่ย error rate ทั้งสี่ในระดับ destination host

ไม่ได้สร้าง count ลบ srv_count หรือ srv_count หาร count เพราะตัวนับทั้งสองมีนิยามและกลุ่มอ้างอิงต่างกัน การเอามาลบหรือหารอาจทำให้เข้าใจผิดว่าเป็นจำนวนหรือสัดส่วนที่ถูกต้อง

หมวดข้อความสามตัวถูกแปลงด้วย One-Hot Encoding protocol มี 3 หมวด คือ icmp, tcp และ udp; service มี 70 หมวด; flag มี 11 หมวด คือ oth, rej, rsto, rstos0, rstr, s0, s1, s2, s3, sf และ sh รวมเป็น 84 คอลัมน์ตัวเลข คอลัมน์ service ในผลลัพธ์ตั้งชื่อตามรูปแบบ service_ตามด้วยชื่อหมวด เช่น service_http หมายถึง record นี้ถูกจัดอยู่ในหมวด HTTP ค่า 1 หมายถึงอยู่ในหมวดนั้น ค่า 0 หมายถึงไม่ใช่หมวดนั้น ไม่ได้สร้างลำดับว่าหมวดใดมากกว่าหมวดอื่น

เพื่อให้อ่านหมวด service ได้เข้าใจง่ายขึ้น เราจะแบ่งชื่อที่พบใน Train ตามหน้าที่คร่าว ๆ แต่เก็บชื่อเดิมในวงเล็บไว้ เพราะชื่อในวงเล็บคือค่าจริงที่อยู่ในไฟล์และเป็นชื่อที่ One-Hot Encoder ใช้

กลุ่มเว็บและการค้นข้อมูล ได้แก่ เว็บ HTTP (`http`) รวมชื่อที่ระบุพอร์ตหรือบริการเว็บแบบเก่า (`http_2784`, `http_443`, `http_8001`), การเรียกดูเอกสารแบบ Gopher (`gopher`) และบริการรวบรวมหรือค้นข้อมูลบนเว็บยุคเก่า (`harvest`) ส่วน `z39_50` เป็นมาตรฐานค้นและดึงข้อมูลจากแหล่งบรรณานุกรมหรือห้องสมุด ชื่อ `http_443` มักสัมพันธ์กับ HTTPS ในระบบเครือข่ายทั่วไป แต่ค่าหมวดนี้เพียงอย่างเดียวไม่ยืนยันว่าข้อมูลถูกเข้ารหัสจริง

กลุ่มชื่อเครื่องและการแปลงชื่อ ได้แก่บริการ DNS หรือชื่อโดเมน (`domain`, `domain_u`), การค้นชื่อ (`name`) และบริการชื่อเครื่อง (`hostnames`) ชื่อที่ลงท้ายด้วย `_u` ในชุดนี้สื่อถึงบริการที่ใช้ UDP เช่น DNS ผ่าน UDP

กลุ่มรับส่งไฟล์และอีเมล ได้แก่ FTP สำหรับควบคุมการส่งไฟล์ (`ftp`) และช่องส่งข้อมูลไฟล์ (`ftp_data`), TFTP ผ่าน UDP (`tftp_u`), ส่งอีเมล (`smtp`), รับอีเมลด้วย POP รุ่น 2 และ 3 (`pop_2`, `pop_3`) และอ่านอีเมลด้วย IMAP4 (`imap4`) ส่วน `mtp` เป็นชื่อโปรโตคอลรับส่งข้อความรุ่นเก่า ไม่ควรเหมารวมว่าเหมือน SMTP ทุกประการ

กลุ่มข่าวและการสื่อสาร ได้แก่ระบบข่าว Usenet (`nntp`, `nnsp`), การสื่อสารผ่าน AOL รุ่นเก่า (`aol`) และการคุยผ่าน Internet Relay Chat (`irc`) ส่วน `uucp` และ `uucp_path` เกี่ยวกับระบบส่งข้อความหรือไฟล์ระหว่างเครื่องแบบ UUCP รุ่นเก่า

กลุ่มเข้าสู่ระบบและสั่งงานระยะไกล ได้แก่ Telnet (`telnet`), SSH (`ssh`), remote shell (`shell`), การเข้าสู่ระบบด้วย Kerberos (`klogin`), Kerberos remote shell (`kshell`), บริการเข้าสู่ระบบ (`login`), สั่งรันโปรแกรมระยะไกล (`exec`), ตรวจสอบชื่อผู้ใช้หรือการยืนยันตัวตน (`auth`) และสอบถามข้อมูลผู้ใช้ (`finger`) ส่วน `supdup` เป็นโปรโตคอล terminal ระยะไกลแบบเก่า

กลุ่มเครือข่ายและระบบเฉพาะ ได้แก่แลกเปลี่ยนเส้นทางระหว่างเครือข่าย (`bgp`), บริการชื่อและ session ของ NetBIOS (`netbios_ns`, `netbios_ssn`) รวมถึงส่ง datagram ของ NetBIOS (`netbios_dgm`), บริการ directory (`ldap`), เรียก procedure ระยะไกล (`sunrpc`, `courier`), ติดต่อฐานข้อมูล Oracle แบบ SQL*Net (`sql_net`), ดูสถานะเครือข่ายหรือเครื่อง (`netstat`, `systat`), ค้นข้อมูลผู้จดทะเบียนโดเมน (`whois`), พิมพ์งาน (`printer`), แสดงผลกราฟิก X Window (`x11`) และส่งงานไปประมวลผลระยะไกล (`remote_job`, `rje`)

กลุ่มเวลาและบริการพื้นฐาน ได้แก่สอบถามเวลาหรือวันที่ (`time`, `daytime`), ซิงก์นาฬิกา NTP ผ่าน UDP (`ntp_u`), ส่งข้อความสะท้อนกลับ (`echo`) และบริการที่รับข้อมูลแล้วทิ้ง (`discard`)

กลุ่ม ICMP ใช้ชื่อย่อที่ลงท้ายด้วย `_i` ได้แก่ขอ echo (`eco_i`), ตอบ echo (`ecr_i`), แจ้ง redirect (`red_i`), แจ้งเวลา (`tim_i`), แจ้งปลายทางหรือ host ไปไม่ถึง (`urh_i`) และแจ้งว่า port ไปไม่ถึง (`urp_i`) กลุ่มนี้เป็นชื่อประเภทข้อความ ICMP ไม่ใช่เว็บหรือแอปพลิเคชันที่เปิดใช้งานบนพอร์ตแบบ TCP ทั่วไป

ยังมีหมวดเฉพาะหรือชื่อเก่าที่ชื่อเพียงอย่างเดียวบอกแอปจริงได้ไม่ครบ ได้แก่ `csnet_ns`, `ctf`, `efs`, `iso_tsap`, `link`, `pm_dump`, `vmnet` และ `private`; ส่วน `other` หมายถึงบริการที่ไม่เข้าชื่อมาตรฐานในรายการนี้ ไม่ควรเดาความหมายละเอียดกว่านี้จาก label เพียงอย่างเดียว

การจัดกลุ่มข้างต้นเป็นคำอธิบายเพื่อช่วยเรียน ไม่ได้แปลว่าทุก record ที่มีชื่อ service นั้นพิสูจน์ว่าปลายทางรันแอปดังกล่าวจริง เพราะคอลัมน์นี้เป็นค่าหมวด service ที่ dataset บันทึกไว้ ไม่ใช่การตรวจสอบซอฟต์แวร์ปลายทางโดยตรง รายชื่อบริการและคำอธิบายพื้นฐานอ้างอิงคำอธิบายฟีเจอร์ของ KDD Cup; ชื่อเก่าหรือชื่อเฉพาะที่แหล่งข้อมูลไม่ขยายความจะคงไว้ตามชื่อเดิม

Vocabulary ของ One-Hot เรียนจาก KDDTrain เท่านั้น แล้วใช้ลำดับคอลัมน์เดียวกันกับ Test และ Test-21 ถ้าพบหมวดที่ไม่มีใน Train จะบันทึกใน unknown_category_report รอบปัจจุบันเอกสารระบุว่าไม่พบหมวดใหม่

ผล full feature set จึงมี numeric เดิม 37 บวก engineered 36 บวก One-Hot 84 รวม 157 คอลัมน์ ส่วน targets มี label, attack_family และ is_attack แยกเป็นไฟล์อีกสามคอลัมน์ รายงาน validation ตรวจแถว feature กับ target ว่าจับคู่กัน จำนวนคอลัมน์ตรงกัน ไม่มี missing หรือ infinity และ schema ของทุก split ตรงกับ Train

แต่ Isolation Forest baseline ปัจจุบันเลือกเพียง numeric เดิม 37 กับ One-Hot 84 รวม 121 คอลัมน์ ยังไม่ใช้ engineered เพิ่ม 36 ตัว เหตุผลคือบาง feature ซ้ำกับข้อมูลเดิม การเพิ่มหลายสำเนาของสัญญาณอาจทำให้มันมีอิทธิพลต่อการแบ่งต้นไม้มากเกินไป จึงต้องทดลองเปรียบเทียบทีละกลุ่ม

Notebook นี้ไม่ scale ข้อมูลเอง เพราะขั้น scale ต้อง fit ด้วย Train และนำตัวแปลงเดียวกันไปใช้กับ validation หรือ test ภายใน pipeline ของโมเดล ไม่ควรคำนวณค่าเฉลี่ยหรือส่วนเบี่ยงเบนจาก Test

เหตุผลของการเพิ่มฟีเจอร์แต่ละกลุ่มมาจากสิ่งที่ EDA เปิดให้เห็น: log transform ใช้กับตัวเลขที่หางยาว, indicator ใช้เก็บข้อมูลว่าเหตุการณ์หายากเกิดขึ้นหรือไม่ และ one-hot ใช้แทนหมวดหมู่โดยไม่สร้างลำดับเทียม Aggregate ใช้สรุปหรือเก็บทิศทางของข้อมูลหลายช่อง แต่สูตรแต่ละตัวต้องมีความหมายตรวจสอบได้ ผลที่ได้คือชุด full 157 คอลัมน์สำหรับทดลอง และชุดที่ trainer baseline เลือก 121 คอลัมน์ ไม่ได้หมายความว่าชุดที่มีคอลัมน์มากกว่าจะทำคะแนนดีกว่า

ที่มาสำหรับว่าฟีเจอร์ไหนสร้างอย่างไรคือ feature engineering notebook, config และ schema ที่บันทึกสูตรกับลำดับคอลัมน์ ส่วนรายงาน validation ยืนยันจำนวนแถวและความตรงกันของ features กับ targets การเพิ่มฟีเจอร์จึงเป็นสมมติฐานที่ต้องทดสอบกับ validation/test ไม่ใช่ข้อสรุปว่าความแม่นยำดีขึ้นแล้ว

## บทที่ 7: Label การโจมตีและ Isolation Forest

Label ใน NSL-KDD มาจากสถานการณ์ในชุดข้อมูลที่ผู้จัดทำกำหนดและติดป้ายไว้ ไม่ได้มีคำบรรยายทุกแถวว่าคอลัมน์ใดทำให้เกิดการโจมตี Feature อาจช่วยอธิบายว่าทำไมโมเดลมองแถวนั้นแปลก แต่ไม่ใช่หลักฐานว่าฟีเจอร์เป็นสาเหตุจริง

ใน Train พบ 23 labels คือ normal กับ attack 22 ชนิด ส่วน KDDTest มี 38 labels คือ normal กับ attack 37 ชนิด รวมทั้ง Train และ Test มีชื่อ label ทั้งหมด 40 แบบ ชุด Test มี attack 17 ชนิดที่ไม่อยู่ใน Train ได้แก่ apache2, httptunnel, mailbomb, mscan, named, processtable, ps, saint, sendmail, snmpgetattack, snmpguess, sqlattack, udpstorm, worm, xlock, xsnoop และ xterm นี่คือเหตุผลที่ทดสอบ unseen attack ได้ แต่ไม่ได้รับประกันว่าจะตรวจพบได้ทุกชนิด

ใน mapping ของโปรเจกต์ DoS มี back, land, neptune, pod, smurf และ teardrop; Probe มี ipsweep, nmap, portsweep และ satan; R2L มี ftp_write, guess_passwd, imap, multihop, phf, spy, warezclient และ warezmaster; U2R มี buffer_overflow, loadmodule, perl และ rootkit ส่วน normal คือ Normal ชื่อที่เหลือใน Test ได้ Unknown ใน attack_family ปัจจุบัน แต่ is_attack ยังเป็นหนึ่งและ label เดิมไม่หาย

เมื่ออธิบาย taxonomy ทั้งชุดตามเอกสาร NSL-KDD รายชื่อ DoS ที่ยกตัวอย่างเพิ่มเติมมี apache2, mailbomb, processtable, udpstorm และ worm ด้วย กลุ่ม Probe มี mscan และ saint เพิ่มเติม กลุ่ม R2L มี httptunnel, named, sendmail, snmpgetattack, snmpguess, xlock และ xsnoop ส่วนเอกสารจัด ps, sqlattack และ xterm ไว้ในกลุ่ม U2R ด้วย

ขอเน้นว่า taxonomy ที่ใช้เพื่ออธิบายกับ mapping ที่เขียนอยู่ใน pipeline ไม่เหมือนกันทั้งหมด การเห็นชื่ออยู่ในตารางคำอธิบายไม่ได้แปลว่าโค้ด attack_family map ปัจจุบันจัดชื่อนั้นเข้า family แล้ว จึงต้องตรวจ mapping ก่อนใช้ attack_family เป็น y ของ supervised model

Isolation Forest ทำงานโดยสร้างต้นไม้สุ่มเพื่อแยก record ถ้าพฤติกรรมแยกตัวได้เร็วหรือมีเส้นทางสั้นในต้นไม้หลายต้น โมเดลมักให้คะแนน anomaly สูง ในโปรเจกต์คะแนนนิยามเป็นลบของ score_samples ดังนั้นคะแนนยิ่งสูงยิ่งน่าสงสัย แล้วเปรียบเทียบ threshold เพื่อแจ้งเตือน

ตัวอย่าง backup ที่อธิบายในเอกสารใช้ Isolation Forest 300 ต้นไม้, seed 42, Train 125,973 แถว และ feature 121 คอลัมน์ Threshold ประมาณ 0.44345 ถูกคำนวณจากคะแนน Train ตาม quantile ที่ตั้งไว้ Label ไม่ได้เข้า fit และ threshold ไม่ใช่ความน่าจะเป็น ไม่ได้หมายความว่ามีโอกาสโจมตี 44 เปอร์เซ็นต์

การอธิบาย SHAP ในเอกสารคำนวณกับ anomaly score ที่โมเดลใช้จริง โดยใช้ background จาก Train และตรวจแล้วว่าผลรวม base value กับ SHAP กลับมาใกล้คะแนนจริงมาก ความคลาดเคลื่อนสูงสุดประมาณ 2.8 คูณสิบยกกำลังลบ 16 ค่า SHAP บวกหมายถึงดันคะแนนของ record นั้นขึ้น ค่า SHAP ลบหมายถึงดึงลงเมื่อเทียบกับ baseline ของ SHAP ไม่ใช่เหตุและผล

ตัวอย่างเช่น record warezmaster หมายเลข KDDTest แถว 17093 ได้คะแนน 0.48808 สูงกว่า threshold 0.44345 จึงเป็น TP เมื่อเทียบกับ label จริง SHAP ที่ดันคะแนนคือ service FTP และการใช้ guest login โมเดลจึงมองรูปแบบนี้ว่าน่าสงสัยภายใต้ข้อมูลที่เรียนรู้ แต่เราไม่สามารถสรุปว่า FTP หรือ guest login เป็นสาเหตุของ attack

อีกตัวอย่าง record normal KDDTest แถว 09658 ได้คะแนน 0.47683 จึงเกิน threshold กลายเป็น False Positive แม้ label จะเป็น normal ส่วน record smurf แถว 01491 ได้คะแนนใกล้ threshold แต่ยังต่ำกว่าเล็กน้อย จึงเป็น False Negative ตัวอย่างเหล่านี้สอนว่า anomaly ไม่เท่ากับ attack และการไม่แจ้งเตือนไม่ได้แปลว่าปลอดภัย

ผลประเมิน backup บน KDDTest มี 22,544 แถว, TP 2,152, FP 70, FN 10,681 และ TN 9,641 Precision 96.85 เปอร์เซ็นต์ แต่ Recall 16.77 เปอร์เซ็นต์ และ F1 ประมาณ 0.2859 ROC-AUC 0.8796 บน KDDTest-21 มี Precision 96.88 เปอร์เซ็นต์, Recall 22.08 เปอร์เซ็นต์, F1 0.3596 และ ROC-AUC 0.6450

การอ่านผลคือเมื่อโมเดลแจ้งเตือน มักตรงกับ attack ในชุดทดสอบนี้ แต่โมเดลพลาด attack จำนวนมาก จึงไม่ควรใช้คำว่าไม่แจ้งเตือนแปลว่าปลอดภัย ตัวอย่าง record ราย label มีไว้ดูความต่างของคะแนน และตัวอย่าง TP, FP, FN, TN ช่วยแยกว่าโมเดลแจ้งอย่างไรเทียบกับ label จริง ส่วน cluster ID จาก K-Means เป็นหมายเลขกลุ่ม ไม่ใช่ DoS หรือชื่อ attack โดยอัตโนมัติ

ที่มาของ label จริงคือ annotation ที่มากับ benchmark ส่วน anomaly score มาจากการคำนวณของ Isolation Forest ซึ่งตามหลักการจะแยกตัวอย่างที่ถูกแยกได้ด้วยเส้นทางสั้นในต้นไม้สุ่มให้ดูผิดปกติมากขึ้น ผลสองอย่างนี้ตอบคนละคำถาม: label บอกว่าผู้จัดทำชุดข้อมูลกำกับ record ไว้อย่างไร ส่วน score บอกว่า record แตกต่างจากข้อมูลที่โมเดลเรียนรู้แค่ไหน การนำมาเทียบกันจึงใช้วัดผลภายหลังเท่านั้น และไม่เปลี่ยนการฝึกแบบ unsupervised ให้กลายเป็น supervised

คะแนนและ metric ในบทนี้เป็นผลของ backup model กับ split และ threshold ที่ระบุไว้ ไม่ใช่คุณสมบัติสากลของ Isolation Forest การที่ Precision สูงแต่ Recall ต่ำแปลว่าแจ้งแล้วมักตรง แต่ยังพลาดการโจมตีจำนวนมาก จึงต้องพิจารณาความเสี่ยง false negative และบริบทการใช้งานด้วย

## บทที่ 8: UNSW-NB15 และ EDA

UNSW-NB15 สร้างใน Cyber Range ของ UNSW Canberra โดยจำลองกิจกรรมปกติและการโจมตี แล้ววิเคราะห์ traffic เป็น record พร้อม feature และ label ชุด official training มี 175,341 แถว ส่วน testing มี 82,332 แถว ชุดข้อมูลมีทั้ง traffic จำลองและปกติ จึงเป็น benchmark สำหรับการทดลอง ไม่ใช่ตัวแทนทุกเครือข่ายจริง

คำเตือนจากการตรวจไฟล์ครั้งนี้คือเอกสาร UNSW บางย่อหน้ายังบอกว่าในเครื่องไม่มี raw data แต่ไฟล์จริงและรายงานในเครื่องปัจจุบันมีอยู่แล้ว ให้ยึดรายงาน EDA, checksum, readiness และ build ที่สร้างจากไฟล์จริงเป็นหลัก สถานะไฟล์เปลี่ยนได้ตามเครื่องและเวลา

Notebook EDA ของ UNSW เริ่มจากอ่าน sample ไม่เกิน 20,000 แถวต่อไฟล์เพื่อเช็ก header, ชนิดข้อมูล, missing และจำนวนค่าที่ไม่ซ้ำ รายงาน sample ใช้ดู schema เร็ว แต่ไม่ใช่สถิติเต็ม dataset จากนั้น notebook ยังมีส่วนวิเคราะห์เต็ม Train และ Test ทุกแถว เพื่อรายงาน label, missing, duplicates และสถิติตัวเลขอย่างครบกว่า

รายงานเต็มที่มีในเครื่องพบ Train 175,341 แถว, Test 82,332 แถว และ 45 คอลัมน์ในทั้งคู่ ไม่พบ missing cell หรือ duplicate แบบตรงกันในสองไฟล์ Train มี Normal 56,000 แถว หรือ 31.94 เปอร์เซ็นต์ Attack ประมาณ 68.06 เปอร์เซ็นต์ Test มี Normal 37,000 แถว หรือ 44.94 เปอร์เซ็นต์ และ Attack ประมาณ 55.06 เปอร์เซ็นต์

UNSW มีหมวด attack 9 กลุ่ม คือ Analysis, Backdoor, DoS, Exploits, Fuzzers, Generic, Reconnaissance, Shellcode และ Worms บางกลุ่มพบได้น้อยมาก เช่น Worms มี 130 แถวใน Train และ 44 ใน Test ขณะที่ Generic และ Exploits มีจำนวนมากกว่า ความไม่สมดุลนี้มีผลต่อวิธีประเมินผล

กราฟการกระจายตัวเลขจะแสดงค่าเฉลี่ย ควอไทล์ เปอร์เซ็นต์ศูนย์ ความเบ้ และค่านอกกรอบ IQR พร้อมกราฟ log1p โดยไม่ลบหรือ clip ค่า การเปรียบเทียบ Normal กับ Attack หรือ correlation ใช้ label เพื่อสำรวจเท่านั้น ไม่ใช่การฝึก unsupervised และไม่พิสูจน์เหตุและผล

ข้อสรุปจาก EDA คือควรตรวจ schema จริงและสัดส่วน label ก่อนใช้ ไม่ลบ outlier โดยอัตโนมัติ และตรวจความต่าง Train กับ Test โดยเฉพาะฟิลด์ที่จำเป็นต่อ Harmonization หากคอลัมน์ที่คาดไว้หาย ให้ตรวจรุ่นและ header แทนการหยิบคอลัมน์จากตำแหน่งเดา

เหตุผลที่ UNSW EDA มีทั้ง sample และการตรวจเต็มชุด คือ sample ช่วยพบปัญหา header และชนิดข้อมูลได้เร็ว แต่การสรุปจำนวน label, duplicate และคุณภาพของทุกแถวต้องใช้ข้อมูลเต็ม ที่มาของตัวเลขฉบับนี้คือไฟล์ official train/test ที่อยู่ใน raw และรายงาน EDA เต็มซึ่งสร้างในโปรเจกต์ ผลที่ได้ยืนยันว่าทั้งสอง split มี 45 คอลัมน์และจำนวนแถวตามรายงาน พร้อมแสดงความต่างของสัดส่วน Normal/Attack และ attack group ซึ่งต้องนำไปประกอบการเลือก metric และตรวจ domain shift

การที่รายงานไม่พบ missing หรือ duplicate ในไฟล์ชุดนี้หมายถึง “ไม่พบตามนิยามและรอบที่ตรวจ” ไม่ได้พิสูจน์ว่า flow ทุกแถวเป็นตัวแทนการใช้งานจริง หรือไม่มีปัญหาเชิงความหมายของฟีเจอร์

## บทที่ 9: Cleansing และ Harmonization ของ UNSW-NB15

ไฟล์ UNSW ต้องวางในโฟลเดอร์ raw ด้วยชื่อ official training-set และ testing-set โดยรักษา header และค่าต้นฉบับ download.py ในโฟลเดอร์นี้ตรวจไฟล์ที่วางไว้ ขนาด และ checksum แต่ไม่ได้ข้ามหน้าเข้าสู่ระบบเพื่อดาวน์โหลดไฟล์ SharePoint ให้ดาวน์โหลดด้วยบัญชีที่ได้รับอนุญาตก่อน

Notebook cleansing อ่านข้อมูลทีละ chunk เพื่อไม่ต้องเก็บไฟล์ทั้งหมดในหน่วยความจำ ปรับ BOM และช่องว่างรอบชื่อคอลัมน์กับข้อความ ถ้าปรับแล้วชื่อคอลัมน์ชนกันจะหยุด sentinel เช่นข้อความว่าง, nan, null, n/a และ infinity ที่สื่อว่าข้อมูลหาย จะกลายเป็น missing ไม่ใช่ศูนย์

แต่ละแถวได้รับ orig_row_id ที่อ้างถึงไฟล์และตำแหน่งแถว ส่วน duplicate flag ทำเครื่องหมายแถวที่ซ้ำกับแถวก่อนหน้าในไฟล์เดียวกัน แต่ไม่ลบแถวนั้นและไม่ตัด outlier อัตโนมัติ การเก็บแถวพร้อม audit ทำให้ตัดสินใจภายหลังได้โดยไม่สูญเสียหลักฐาน รายงานแสดงจำนวนเซลล์ที่เปลี่ยน จำนวนแถวซ้ำที่ถูกทำเครื่องหมาย และจำนวนแถวเข้าออกแต่ละ chunk

รายงาน EDA เต็มของ raw ที่มีอยู่ไม่พบ missing หรือ duplicate อยู่แล้ว แต่กติกา cleansing ยังจำเป็นเพื่อทำให้ข้อมูลรุ่นใหม่สม่ำเสมอและตรวจความเปลี่ยนแปลงได้ ไฟล์ต้นฉบับจะไม่ถูกแก้

Harmonization ของ UNSW ตรวจ checksum ว่า raw ยังตรงกับ manifest แล้วอ่านคอลัมน์ด้วยชื่อ header จริง ไม่ใช่ตำแหน่ง dur กลายเป็น duration, proto เป็น protocol, sbytes เป็น bytes_forward และ dbytes เป็น bytes_backward โดยเก็บทิศทางไว้

service ถูกจัดเข้ากลุ่ม DNS, FTP, HTTP, HTTPS/SSL, SMTP, SSH หรือ other ส่วน state ถูกจัดเป็น established, no-reply, reset หรือ other เป็นการย่อหมวดเพื่อให้ทั้งสอง Dataset ใช้ vocabulary กลางเดียวกัน แต่ mapping แบบหยาบไม่ได้รักษารายละเอียดทุกสถานะต้นฉบับ

label ต้นทางเป็นเลขศูนย์สำหรับ normal และหนึ่งสำหรับ attack ส่วน attack_cat เก็บชื่อกลุ่มเดิม แล้ว map เข้าหมวดกลาง: Normal หรือ Benign เป็น Normal; DoS เป็น DoS/DDoS; Reconnaissance เป็น Probe/Recon; Exploits และ Shellcode เป็น Exploit/U2R; Backdoors และ Worms เป็น Botnet/Backdoor; Fuzzers, Generic และ Analysis เป็น Generic/Fuzzer; ค่าที่ไม่เข้ากลุ่มเป็น Other attack

การ map นี้เป็น taxonomy ของโปรเจกต์เพื่อเปรียบเทียบข้ามแหล่ง ไม่ใช่ taxonomy สากลครบถ้วน label เดิมยังเก็บไว้ และถ้า label เป็นศูนย์แต่ category ไม่ใช่ normal ระบบหยุดให้ตรวจแทนการแก้ label ให้เอง

UNSW ยังมี spkts และ dpkts สำหรับจำนวน packet สองทิศทาง, sttl และ dttl สำหรับ TTL, swin และ dwin สำหรับ TCP window และ stime สำหรับเวลาเริ่มต้นถ้ามี ค่าเหล่านี้เป็น extension เฉพาะชุด NSL ไม่มีคอลัมน์ที่เทียบตรงกัน จึงไม่เข้า core model profile โดยอัตโนมัติ mean_packet_size คำนวณได้จาก bytes รวม หารด้วย packet รวม เมื่อ packet count มากกว่าศูนย์เท่านั้น

คอลัมน์อื่น เช่น rate, sload, dload, sloss, dloss, timing, jitter, TCP details, HTTP/FTP context และ ct counters ถูกเก็บเพื่อ audit แต่ยังไม่ถูกส่งเข้า feature กลางจนกว่าจะกำหนดหน่วยและความหมายใน contract IP, port, Flow ID และ timestamp ดิบเป็นตัวระบุหรือ metadata ไม่ใช่ feature กลางอัตโนมัติ เพราะโมเดลอาจจำแหล่ง capture แทนพฤติกรรม

ผล Harmonization มี features, labels และ metadata แยกกัน ข้อมูลตัวเลขที่ผิดหรือไม่มีค่าถูกทำเป็น missing และมี quality flag โดยไม่ลบแถวเงียบ ๆ คอลัมน์ optional ที่ไม่มีทั้ง field จะเป็น null พร้อม availability mask

ทำ Cleansing ของ UNSW เพื่อแก้ความไม่สม่ำเสมอของไฟล์ตารางโดยไม่ทำให้ข้อมูลที่หายไปดูเหมือนศูนย์ เหตุผลเรื่อง chunking มาจากขนาดไฟล์และข้อจำกัดหน่วยความจำ ส่วนการเก็บ orig_row_id และ audit ช่วยตรวจย้อนกลับว่ามีอะไรถูก normalize หรือถูกทำเครื่องหมายบ้าง ผลการตรวจจริงจึงควรอ่านจาก cleansing_audit: จำนวนแถวเข้าออก ค่าที่กลายเป็น missing และธง duplicate; duplicate flag ไม่ได้แปลว่าลบแถวนั้นแล้ว

จากนั้น Harmonization ใช้ schema และ mapping ที่ตรวจเทียบกับคู่มือฟีเจอร์ต้นทาง เหตุผลที่เก็บคอลัมน์เฉพาะ UNSW ไว้เป็น extension คือเราไม่ควรยัดค่าที่เทียบไม่ได้เข้ากับ NSL ผลคือ core กลางที่เทียบกันได้ พร้อมตาราง labels และ metadata แยกกัน และยังเก็บรายละเอียดเพิ่มเติมไว้ให้ทดลองในอนาคต

## บทที่ 10: สร้าง Dataset กลางและแบ่งชุดข้อมูล

Notebook common build_dataset รับผล Harmonization ของ NSL และ UNSW ไม่ทำ cleansing หรือ Harmonization ซ้ำ ขั้นแรกตรวจ SHA-256 ของ raw และ version ของ dataset registry กับ feature contract จากนั้นยืนยันว่า features, labels และ metadata มี record_id ตรงกันและมี provenance ครบ

ถ้าชุดหนึ่งยังไม่พร้อม รายงาน readiness จะอธิบายสาเหตุ และ build อาจใช้เฉพาะชุดที่พร้อมได้ แต่ผลแบบ source_local_diagnostic ไม่ใช่หลักฐานว่าทดลองข้าม Dataset แล้ว หากไม่มีชุดใดพร้อมจะหยุด ส่วน feature compatibility จะบอกว่า feature ใช้ได้ใน build นี้หรือได้รับการยืนยันครบทุกแหล่งตามเงื่อนไขเชิงเทคนิค

คำว่า eligible หรือพร้อมทางเทคนิคไม่ได้พิสูจน์ว่าความหมายทางสถิติเท่ากัน ต้องตรวจเอกสาร source เรื่องหน่วย ทิศทาง และวิธีเก็บข้อมูลด้วย

ผลรอบล่าสุดในเครื่องมี NSL-KDD 148,517 แถวและ UNSW-NB15 257,673 แถว รวม 406,190 records รายงาน readiness ระบุว่าทั้งคู่พร้อม ข้อมูลตัวเลขนี้เป็นสถานะของ output ปัจจุบัน ไม่ใช่ค่าคงที่เมื่อทุกคน clone repository

การแบ่งชุดเก็บ official Test ของแต่ละ Dataset ไว้ Validation จำนวน 20 เปอร์เซ็นต์มาจาก official Train ด้วย seed 42 และไม่อ่าน label train_full คือส่วนที่เหลือจาก official Train หลังแยก validation ส่วน train คือชุดย่อยที่สุ่มจำนวนแถวให้เท่ากันต่อแหล่งเมื่อมีหลาย Dataset

ในผลปัจจุบัน train มี NSL 100,778 แถว และ UNSW 100,778 แถว รวม 201,556 แถว train_full มี NSL 100,778 และ UNSW 140,273 รวม 241,051 แถว validation มี NSL 25,195 และ UNSW 35,068 รวม 60,263 แถว ส่วน test มี NSL 22,544 กับ UNSW 82,332 รวม 104,876 แถว

การสุ่มให้จำนวนเท่ากันเป็นการสมดุลจำนวนแถวตามแหล่งข้อมูล ไม่ได้ทำให้ Normal กับ Attack มีจำนวนเท่ากัน และไม่ได้กรองเฉพาะ Normal เพราะขั้นนี้ไม่ใช้ label sample_weight เป็น metadata ไม่ใช่ feature

KDDTest-21 เป็น view ที่ชี้ไปยัง 11,850 แถวใน KDDTest ไม่ถูกนำมาต่อซ้ำเป็น record ใหม่ รายงานใน common/output/reports มี readiness, compatibility, split counts, build summary และรายการ view ของ Test-21 ใช้ตรวจความสำเร็จก่อนฝึกโมเดล

เหตุผลที่ common ตรวจ readiness และ compatibility ก่อนรวม คือการรวมไฟล์ให้สำเร็จทางเทคนิคยังไม่รับประกันว่าความหมายเข้ากัน ผล readiness บอกว่าไฟล์และตารางเชื่อมกันครบหรือไม่ ส่วน compatibility บอกสถานะตามกฎ contract; ทั้งคู่เป็นด่านตรวจ ไม่ใช่คะแนนคุณภาพโมเดล

การเก็บ official Test ไว้ไม่แตะระหว่างสร้าง Train/Validation ช่วยให้มีชุดประเมินที่ไม่ใช้สร้างตัวแปลงหรือเลือกพารามิเตอร์ ส่วนการสุ่มจำนวน record เท่ากันต่อ source ลดโอกาสที่ชุดใหญ่จะครองสัดส่วนตัวอย่างใน Train แต่ไม่ได้แก้ class imbalance ภายใน source ผล output แสดงขนาด split และ source counts เพื่อให้เห็นอย่างโปร่งใสว่าแต่ละชุดมีข้อมูลจากไหนและจำนวนเท่าไร

## บทที่ 11: Feature Engineering กลาง joint_v1 ทั้ง 19 คอลัมน์

Notebook common feature_engineering อ่าน split ที่ build สร้าง ตรวจว่า record_id ในสามตารางตรงกัน และคอลัมน์ที่จำเป็นครบ หากมีค่าว่างหรืออนันต์ใน feature บังคับ ระบบหยุดแทนการเติมศูนย์หรือลบแถวโดยไม่บอก

profile joint_v1 มี numeric features สี่คอลัมน์ และ one-hot features อีกสิบห้าคอลัมน์ รวม 19 model features โดยไฟล์ยังมี record_id อีกหนึ่งคอลัมน์ไว้ join แต่ต้อง drop ก่อน fit หรือ predict

คอลัมน์ตัวเลขตัวแรก log_duration มาจาก duration ผ่าน log1p แล้ว StandardScaler จึงบอกว่าระยะเวลาเชื่อมต่อต่ำหรือสูงเมื่อเทียบกับ Train ค่าหลัง scaler ที่ติดลบไม่ได้หมายถึงเวลาติดลบ แค่ต่ำกว่าค่าเฉลี่ย Train

log_bytes_forward มาจาก bytes ขาไป และ log_bytes_backward มาจาก bytes ขากลับ ใช้ log1p แล้วปรับสเกลเหมือนกัน เพื่อไม่ให้ค่าปริมาณที่ใหญ่มากครอบงำช่วงตัวเลข ส่วน signed_log_bytes_ratio คือ log1p ของ bytes ขาไป ลบ log1p ของ bytes ขากลับ ถ้าเป็นบวกแปลว่าขาไปมากกว่า ถ้าลบแปลว่าขากลับมากกว่า ถ้าใกล้ศูนย์ปริมาณใกล้กัน ตัวอย่าง 120 ไบต์กับ 30 ไบต์จะได้ log ของ 121 ลบ log ของ 31 ประมาณบวก 1.36 ก่อน scale ถ้าสลับทิศทางจะได้ประมาณลบ 1.36

protocol มีสี่คอลัมน์ คือ protocol_tcp, protocol_udp, protocol_icmp และ protocol_other แต่ละแถวต้องเปิดหนึ่งช่องพอดี protocol_other ใช้กับค่าที่รู้จักว่าไม่เข้า TCP, UDP หรือ ICMP หรือค่าที่ map ไม่อยู่ในกลุ่ม ค่า missing ไม่ถูกซ่อนเป็น other

service มีเจ็ดคอลัมน์ คือ service_dns, service_ftp, service_http, service_https_ssl, service_smtp, service_ssh และ service_other คำพ้องที่กำหนดใน contract เช่น domain หรือ domain_u ถูกจัดเป็น DNS; ftp_data ถูกจัดเป็น FTP; www ถูกจัดเป็น HTTP; https หรือ ssl ถูกจัดเป็น HTTPS/SSL ค่าที่มีจริงแต่ไม่เข้ากลุ่มใช้ other

สถานะ connection มีสี่คอลัมน์ คือ conn_state_established, conn_state_no_reply, conn_state_reset และ conn_state_other ตัวอย่างสถานะ sf, fin หรือ con อาจถูก map เป็น established; s0, int หรือ req เป็น no-reply; rej, rsto, rstr, rstos0 หรือ rst เป็น reset ส่วนสถานะอื่นเป็น other ชื่อ no_reply เป็นเพียงหมวดหยาบ ไม่ใช่หลักฐานว่าไม่มีแพ็กเก็ตตอบกลับในทุกความหมาย

ในแต่ละกลุ่ม One-Hot ต้องมีหนึ่งคอลัมน์เป็นหนึ่งและคอลัมน์อื่นเป็นศูนย์ จึงแทนหมวดโดยไม่สร้างลำดับปลอม ค่าหมวดที่ไม่รู้จักจัดเข้า other ส่วนช่องว่างของ feature ที่จำเป็นจะหยุดให้ตรวจ

โปรไฟล์ไม่ใส่ log_total_bytes เพราะซ้ำกับข้อมูล bytes สองทิศทาง และไม่ใส่ log_bytes_per_second เพราะ duration ศูนย์ทำให้การใช้ epsilon คำนวณอัตราอาจคลาดเคลื่อนจากความหมายจริง

StandardScaler และ One-Hot Encoder fit จาก train เท่านั้น แล้วใช้ตัวแปลงเดิมกับ train_full, validation และ test การ fit ไม่ใช้ y ค่าเฉลี่ยของ numeric ใน Train หลัง StandardScaler จะใกล้ศูนย์และส่วนเบี่ยงเบนมาตรฐานใกล้หนึ่ง ส่วน validation/test ไม่จำเป็นต้องได้ค่าเหล่านี้ เพราะอาจมี distribution ต่างจาก Train ซึ่งเป็นข้อมูลที่ควรสังเกต ไม่ใช่เหตุให้ fit ใหม่

รายงานปัจจุบันระบุ train 201,556 แถว, train_full 241,051, validation 60,263 และ test 104,876 ทุกชุดมี 19 features ไฟล์ output มี features.csv, labels.csv, metadata.csv แยกตาม split พร้อม preprocessor.joblib, feature_schema.json และ feature_engineering_report.csv

features.csv คือข้อมูลที่เตรียมให้โมเดล ยังไม่ใช่ prediction หรือ anomaly score labels.csv คือคำตอบสำหรับ evaluation metadata.csv ใช้ตามรอย feature_schema เป็นสัญญาระบุชื่อและลำดับคอลัมน์ preprocessor.joblib เก็บ scaler และ encoder ที่ fit แล้ว ส่วน report ใช้ตรวจจำนวนแถวและ feature ไม่ได้บอกว่าโมเดลตรวจ attack ได้ดี

Raw data และ generated outputs ส่วนใหญ่ถูกละเว้นจาก Git เพื่อไม่ให้ repository ต้องเก็บไฟล์ข้อมูลขนาดใหญ่หรือข้อมูลที่สร้างซ้ำได้ สมาชิกที่ clone โปรเจกต์จึงต้องเตรียมไฟล์ raw ตามสิทธิ์การใช้งาน แล้วรัน Notebook เพื่อสร้าง output ของตัวเอง รายงานและกราฟ MLP รุ่นเก่าบางไฟล์เป็นข้อยกเว้นที่ยังเก็บใน repository

เหตุผลที่ joint_v1 เลือกสี่ตัวเลขและสิบห้าหมวดหมู่ คือพยายามเก็บสัญญาณพื้นฐานที่มีในทั้งสองชุดโดยไม่ใส่ตัวระบุเฉพาะแหล่งหรือคอลัมน์ที่ซ้ำความหมาย สูตร signed_log_bytes_ratio ช่วยรักษาว่าข้อมูลไหลไปทางใดมากกว่า ส่วน one-hot ทำให้ protocol, service และ state กลายเป็นตัวเลขโดยไม่มีลำดับสมมติ ที่มาของสูตรและ mapping คือ feature_contract และตัวอย่างข้อมูลจริงใน Harmonization; ผลคือ profile 19 คอลัมน์ที่มี schema คงที่ให้โมเดลอ่าน

การ fit scaler และ encoder ด้วย Train เท่านั้นมีเหตุผลเพื่อไม่ให้สถิติของ Validation/Test แอบมีอิทธิพลต่อ preprocessing หลักการนี้สอดคล้องกับคำแนะนำเรื่องการป้องกัน data leakage ของ scikit-learn ผลที่ควรเห็นคือ preprocessor ถูกบันทึกหนึ่งชุด และใช้แปลง split อื่นโดยไม่ fit ใหม่ หาก Validation/Test มีค่าเฉลี่ยต่างจาก Train นั่นเป็นความต่างของข้อมูลที่ต้องรายงาน ไม่ใช่เหตุให้ปรับตัวแปลงไปตาม Test

เมื่อเปิด output ให้แยกความหมาย: features คือ X ที่พร้อมส่งให้โมเดล, labels คือ y สำหรับตรวจผลภายหลัง, metadata คือข้อมูลตามรอย และ feature schema คือสัญญาว่า X มีชื่อกับลำดับใด ไฟล์เหล่านี้ยังไม่ใช่ผลการทำนายหรือหลักฐานว่าโมเดลดีขึ้น

## บทที่ 12: รันงานอย่างไร และผลนี้บอกอะไร

ลำดับการทำงานเริ่มจากติดตั้ง dependencies ตาม requirements แล้วเตรียม raw data ของทั้งสองชุด จากนั้นเปิด Notebook ของแต่ละ Dataset ตามลำดับ EDA, Cleansing, Harmonization เมื่อทำครบแล้วจึงรัน common build_dataset และสุดท้าย common feature_engineering โมเดลไม่ได้ถูกฝึกอัตโนมัติจากการรัน Data Pipeline

ก่อนเทรน ให้เลือกเฉพาะคอลัมน์ที่อยู่ใน feature_schema แล้วตัด record_id ออกจาก X ห้ามนำ labels หรือ metadata ไปต่อเข้า X สำหรับ Isolation Forest ใช้ X ตอน fit เท่านั้น หลังให้ score แล้วค่อย join labels ด้วย record_id เพื่อวัดผล

ในการประเมิน ควรเลือก threshold จาก Validation ไม่เลือกจาก Test แล้วรายงานผลแยกตาม source และ attack category พร้อม precision, recall, confusion matrix, PR-AUC หรือ ROC-AUC ตามความเหมาะสม ถ้าฝึกจาก NSL แล้วทดสอบ UNSW หรือกลับด้าน จะช่วยวัด domain shift หรือความเปลี่ยนแปลงของรูปแบบระหว่างชุดข้อมูลได้ดีกว่าดูค่าเฉลี่ยรวมอย่างเดียว

Dataset กลางช่วยทำให้ชื่อและโครงสร้างฟีเจอร์เหมือนกัน แต่ไม่ได้ทำให้รูปแบบ traffic ของทุกบริษัทเหมือนกัน และไม่ได้รับประกัน zero-shot detection ในบริษัทใหม่ ต้องทดสอบกับข้อมูลจากแหล่งที่ไม่เคยใช้พัฒนาโมเดล ตรวจอัตรา false alarm และเลือก threshold ให้เหมาะกับงานจริงก่อนใช้งาน

เหตุผลที่เลือก threshold จาก Validation ไม่ใช่ Test คือ Validation ใช้ตัดสินใจในการพัฒนาได้ ส่วน Test ควรเก็บไว้ตอบคำถามสุดท้ายว่าเมื่อล็อกวิธีแล้วจะทำงานอย่างไร การทดสอบข้าม source หรือกับองค์กรใหม่มีไว้ตรวจว่าความหมายเดียวกันของคอลัมน์พอจะรับมือกับ distribution ที่เปลี่ยนหรือไม่ ผลที่ได้อาจต่ำกว่าการทดสอบภายในชุดเดียวกัน และนั่นเป็นข้อมูลสำคัญ ไม่ใช่สิ่งที่ควรซ่อนด้วยการปรับ threshold บน Test

ที่มาของแนวทางเหล่านี้คือหลักการประเมินโมเดลและป้องกัน data leakage ในเอกสาร scikit-learn ส่วนตัวเลขที่รายงานก่อนหน้าเป็นหลักฐานเฉพาะ run ที่มีอยู่เท่านั้น ถ้ามี raw data รุ่นใหม่ ต้องรัน pipeline สร้างรายงานใหม่ แล้วอ้างตัวเลขและ checksum ของรอบนั้น

สิ่งที่ควรจำจากบทเรียนนี้มีสี่ข้อ หนึ่ง Raw คือหลักฐานและไม่แก้ทับ สอง EDA ใช้ตั้งคำถาม ไม่ได้แก้ข้อมูลหรือพิสูจน์เหตุและผล สาม X, y และ metadata ต้องแยกกัน โดย Isolation Forest ไม่ใช้ y ตอน fit และสี่ Feature Engineering เป็นวิธีแทนข้อมูลให้โมเดลเห็นรูปแบบ ไม่ใช่เครื่องรับประกันว่าโมเดลจะดีขึ้น

จบบทเรียน Data Pipeline ตั้งแต่ข้อมูลดิบของ NSL-KDD และ UNSW-NB15 ผ่านการสำรวจ ทำความสะอาด จัดมาตรฐาน รวมและแบ่งชุด จนกลายเป็น 19 features ของ profile joint_v1 สำหรับการทดลองโมเดล

แหล่งอ้างอิงหลักสำหรับที่มาของ Dataset และเหตุผลเชิงวิธีการมีดังนี้

- [เอกสาร SHAP PermutationExplainer](https://shap.readthedocs.io/en/stable/generated/shap.PermutationExplainer.html) ใช้เป็นที่มาของวิธีอธิบาย contribution โดยต้องไม่ตีความ contribution เป็นเหตุและผล
